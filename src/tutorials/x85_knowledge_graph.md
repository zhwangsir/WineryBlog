## 1. 知识图谱是什么：把知识变成网络

知识图谱（Knowledge Graph）用**三元组（实体， 关系， 实体）**表示知识，形成一张巨大的语义网络：

```
（吴承恩， 创作， 西游记）
（西游记， 类型， 四大名著）
（西游记， 主角， 孙悟空）
（孙悟空， 师父， 唐僧）
```

**与关系数据库/文档存储的对比**：

| | 关系库 | 文档库 | 图谱 |
| --- | --- | --- | --- |
| 强项 | 结构化行、强事务 | 灵活文档、单对象完整 | **多跳关系查询** |
| 弱项 | 深层关联要 N 次 JOIN | 关联查询弱 | 无事务、建模成本高 |
| 例 | 用户表+订单表 | 用户文档 | "bob 的好友买过什么" |

**多跳关系查询是图谱的杀手锏**："朋友的朋友中谁在阿里巴巴"——关系库要多层 JOIN（每层成本爆炸），图数据库沿边走两步即得。

## 2. 本体建模：图谱的 schema

本体（Ontology）定义**有哪些类型的实体、哪些类型的关系、属性约束**——图谱的 schema 层：

```
实体类型：人物、作品、组织、地点
关系类型：创作（人物→作品）、就职（人物→组织）、位于（组织→地点）
属性约束：人物有出生日期；作品必有类型
```

建模三问：
1. **业务问题是什么**——图谱为查询而生，schema 由问题倒推（要查"作者的其他作品"就必须有"创作"边）
2. **粒度**：实体拆多细（"孙悟空"与"孙悟空(演员版)"是同实体吗？——同一实体，版本是属性）
3. **方向**：关系要有语义方向（"创作"而非"关联"）——边方向即信息

## 3. 数据模型：属性图 vs RDF

| | 属性图（Neo4j） | RDF 三元组 |
| --- | --- | --- |
| 结构 | 节点+边都可带任意属性 | 纯三元组 (主语， 谓语， 宾语) |
| 查询语言 | **Cypher**（直观图模式） | SPARQL（类 SQL） |
| 标准 | 无官方标准（事实标准） | W3C 标准（语义网体系） |
| 适用 | 应用型图谱（推荐/风控） | 语义网/开放数据互操作 |

Cypher 的图模式查询（直观如画图）：

```cypher
// 查吴承恩创作的作品及其主角
MATCH (a:人物 {name:'吴承恩'})-[r:创作]->(w:作品)<-[r2:主角]-(c:人物)
RETURN w.title, collect(c.name)
```

## 4. 图谱构建流水线：抽取 → 消歧 → 融合

### ① 实体抽取（NER）
从非结构化文本中识别人名/地名/机构/产品。方案：BERT 微调 NER 模型（HuggingFace）或 LLM few-shot 抽取（成本低、精度需抽检）。

### ② 关系抽取
识别实体对之间的关系（"吴承恩 wrote 西游记" → 创作）。方案：规则+词典（高精度窄场景）、远程监督（用已有图谱自动标注语料）、LLM 抽取（泛化强）。

### ③ 实体消歧与对齐（最难的一环）
"苹果"是水果还是公司？——**实体链接**到知识库消歧（上下文分类）；"马云" vs "Jack Ma" vs "马老师"——**实体对齐**合并同一实体的不同写法（属性相似度 + 图结构相似度）。

**质量纪律**：抽取置信度阈值 + 人工抽检校准——垃圾进垃圾出，图谱比关系库更怕脏数据（错误边会污染所有多跳查询）。

## 5. 存储与查询工程

```cypher
// 索引与约束（性能基础）
CREATE INDEX FOR (p:人物) ON (p.name);
CREATE CONSTRAINT FOR (w:作品) REQUIRE w.title IS UNIQUE;

// 多跳查询：两跳内好友的共同兴趣
MATCH (me:人物 {name:'bob'})-[:认识*1..2]->(f:人物)-[:喜欢]->(t:兴趣)
RETURN t.name, count(*) AS n ORDER BY n DESC LIMIT 10
```

规模路径：百万节点内 Neo4j 直接上；亿级用分布式图库（NebulaGraph/JanusGraph）或**关系库模拟**（邻接表存边，两跳查询用两次索引 JOIN——简单场景够用）。

## 6. 应用场景

| 场景 | 图谱的角色 |
| --- | --- |
| 语义搜索 | "吴承恩的作品" → 解析出实体+关系 → 图查询而非关键词匹配 |
| 推荐 | "买了 A 的人也买了"的多跳关联（协同过滤的图版） |
| 风控反欺诈 | 团伙识别：设备/账户/手机号的关联网络环检测 |
| 问答 KBQA | 问题 → 解析实体与意图 → 图查询 → 自然语言回答 |
| 企业知识库 | 部门/系统/人/文档的关联网络（"谁负责这个服务"） |

## 7. LLM 时代的知识图谱：GraphRAG

RAG 的痛点：向量检索适合"语义相似"，**多跳关系问题**（"A 的上级的上级是谁"）检索不到分散的片段。**GraphRAG** 的组合：

```
1. LLM 从文档抽取实体与关系 → 构建轻量图谱
2. 查询时：先定位相关实体 → 沿图谱多跳扩展关联上下文 → 喂给 LLM 生成
```

图谱提供**结构化、精确、可追溯**的关联（补 RAG 的多跳短板）；LLM 提供**语言理解与生成**（补图谱的抽取与表达短板）——互补而非替代（与站内《本地知识库与 RAG 实战》的向量 RAG 并列使用）。

## 8. 陷阱速查表

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 图谱查询结果不可信 | 抽取噪声边污染 | 置信度阈值 + 人工抽检闭环 |
| 同一实体多个节点 | 实体对齐缺失 | 别名表 + 相似度合并 |
| 建模过细无人维护 | 本体过度设计 | 由业务问题倒推 schema |
| 多跳查询变慢 | 无索引/数据量超单机 | 建索引；分布式图库 |
| GraphRAG 检索不到 | 实体抽取漏了关键实体 | 领域词典补充 + 抽检召回率 |
