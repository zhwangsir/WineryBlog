## 1. TCP 的承诺：可靠字节流

IP 层只管"尽力送达"——丢包、乱序、重复都常见。TCP 在其上构建**可靠、有序、面向连接的字节流**：

- **序号（seq）**：每个字节都有编号 → 乱序可重排、丢失可发现
- **确认（ack）**：接收方告知"期望的下一个字节号"→ 累计确认
- **重传**：超时未确认 → 重发
- **流量控制**：接收窗口（rwnd）→ 不压垮接收方
- **拥塞控制**：拥塞窗口（cwnd）→ 不压垮网络

三次握手/四次挥手则是这套机制的门卫：确保双方各自的收发能力都就绪，且断开时双方的数据都发完。

## 2. 三次握手：为什么偏偏是三次

```
客户端                          服务端
CLOSED                          LISTEN
  │── SYN, seq=x ─────────────→│   ① SYN_SENT
  │←─ SYN+ACK, seq=y, ack=x+1 ──│   ② SYN_RCVD
  │── ACK, ack=y+1 ───────────→│   ③ ESTABLISHED（双方）
```

**为什么不是一次**：一次握手 = 客户端单方面宣布连接——服务端无法确认客户端能收（旧连接请求迟到会造成资源浪费）。
**为什么不是两次**：两次握手下，服务端发出 SYN+ACK 就认为连接建立——若客户端的旧 SYN 迟到到达（网络绕路），服务端会白白建立连接等数据（历史连接问题）。三次握手中客户端用最后的 ACK 拒绝/确认，旧 SYN 得到的 SYN+ACK 会被客户端 RST 掉。
**为什么不是四次**：SYN+ACK 可以合并（ACK 顺势捎带），四次多余。

** SYN 洪水攻击（SYN Flood）**：攻击者发 SYN 不回 ACK → 服务端半连接队列爆满。防御：syncookies（用加密编码把状态编码进 SYN+ACK，不占队列）。

## 3. 四次挥手：为什么偏偏是四次

```
主动方                          被动方
ESTABLISHED                     ESTABLISHED
  │── FIN, seq=u ─────────────→│   FIN_WAIT_1        CLOSE_WAIT
  │←─ ACK, ack=u+1 ────────────│   FIN_WAIT_2
  │  （被动方还能发数据！半关闭）    │
  │←─ FIN, seq=w, ack=u+1 ─────│                     LAST_ACK
  │── ACK, ack=w+1 ────────────│   TIME_WAIT         CLOSED
```

**为什么四次而不是三次**：收到 FIN 只代表"对方不再发送"，**被动方可能还有数据没发完**——所以 ACK 与自己的 FIN 分开发（中间夹着数据）。若被动方无数据可发，ACK+FIN 可能合并成三次（延迟确认机制的优化）。

**TIME_WAIT 为什么等 2MSL**（最长报文段寿命的两倍）：
1. 确保最后一个 ACK 若丢失，对方重传 FIN 时还能应答（否则对方收不到确认重发 FIN，无从应答）
2. 让本连接的旧报文在网络中自然消亡，避免污染使用相同四元组的新连接

TIME_WAIT 过多的危害与治理：占用端口与内存（`netstat` 大量 TIME_WAIT）→ 开启 `tcp_tw_reuse`（仅出站连接安全）、端口范围调大（`ip_local_port_range`）。

## 4. TCP 状态机：11 个状态全景

```
           ┌── 三次握手 ──→ ESTABLISHED ── 四次挥手 ──┐
CLOSED ──→ SYN_SENT → SYN_RCVD                FIN_WAIT_1/2 → TIME_WAIT → CLOSED
LISTEN ──→ SYN_RCVD → ESTABLISHED          CLOSE_WAIT → LAST_ACK → CLOSED
```

排查工具：`netstat -ant` / `ss -ant` 看状态分布。**大量 SYN_RCVD** = SYN 洪水；**大量 CLOSE_WAIT** = 你的应用忘了 close()（代码泄漏，最常见！）；**大量 TIME_WAIT** = 本机作为客户端高频短连接（调 reuse）。

## 5. 可靠传输的四大机制

| 机制 | 解决什么 | 要点 |
| --- | --- | --- |
| 校验和 | 传输损坏 | 伪首部+数据反码求和 |
| 序号+确认 | 乱序/丢失 | 累计确认：ack=n 表示 n 前全部收到 |
| 超时重传 | 丢包 | RTO 动态计算（基于 RTT 的 Jacobson 算法） |
| 快速重传 | 丢包 | 收到 3 个重复 ACK → 立即重传（不等超时） |

**RTO 的两难**：太大→丢包恢复慢；太小→误判重传（浪费带宽）。Jacobson/Karels 算法用平滑 RTT（SRTT）与偏差（RTTVAR）动态估计。Karn 算法：重传的报文不计入 RTT 采样（不知道确认的是哪次）。

**SACK（选择性确认）**：累计确认只知"连续到哪"，SACK 附加"哪些块已收到"——让重传更精准（只补洞）。

## 6. 流量控制：滑动窗口

接收方在 ACK 中通告 **rwnd（接收窗口）**= 接收缓冲区剩余空间；发送方保证"已发未确认 ≤ rwnd"——**接收方不被压垮**。

- **零窗口**：接收方缓冲满 → 通告 0 → 发送方停发并启动**坚持定时器**定期发窗口探测（防死锁：窗口更新 ACK 丢了双方僵住）
- **糊涂窗口综合征**：每次通告小窗口导致小包泛滥 → 接收方等缓冲够大再通告（DSACK），发送方 Nagle 算法攒小包

## 7. 拥塞控制：四种算法

发送方维护 **cwnd（拥塞窗口）**，实际发送上限 = min(rwnd, cwnd)：

| 阶段 | 规则 | 曲线 |
| --- | --- | --- |
| 慢启动 | 每RTT cwnd 翻倍（指数） | 指数上升 |
| 拥塞避免 | 达到 ssthresh 后每 RTT +1（线性） | 线性爬升 |
| 快速重传 | 3 个重复 ACK → 立即重传 | 触发 |
| 快速恢复 | cwnd 减半 + ssthresh=当前一半（乘法减小） | 折半后再线性 |

**"加性增、乘性减"（AIMD）** 造就锯齿形曲线——在效率与公平间权衡的分布式算法。现代默认 **CUBIC**（Linux，三次函数增长更激进）；数据中心内 **BBR**（基于带宽与 RTT 测量而非丢包，对抗缓冲区膨胀 bufferbloat）。

## 8. 陷阱速查表

| 现象 | 原因 | 修法/排查 |
| --- | --- | --- |
| 大量 CLOSE_WAIT | 应用收到 FIN 后没调 close | 代码泄漏排查（连接池配置） |
| 大量 TIME_WAIT | 高频短连接（本机为客户端） | tcp_tw_reuse + 长连接化 |
| 传输忽快忽慢锯齿 | 拥塞控制的正常行为 | 非问题 |
| 丢包重传后吞吐骤降 | 传统丢包型拥塞控制对无线网敏感 | BBR / 调 buffer |
| SYN_RCVD 暴涨 | SYN 洪水 | syncookies / 防火墙限速 |
| 首包延迟高 | 握手 RTT（叠加 TLS 更甚） | 连接复用/长连接/TLS 1.3 |
