## 1. 进程：资源的容器

**进程 = 程序 + 一块独立的地址空间 + 资源句柄**。操作系统为每个进程维护：

```
进程控制块 PCB（唯一标识、状态、优先级、寄存器快照）
├── 地址空间：代码段、数据段、堆、栈（虚拟地址，各进程隔离）
├── 资源句柄：打开的文件表、信号处理、网络连接
└── 文件描述符表：fd 0(stdin) 1(stdout) 2(stderr) 起
```

**地址空间隔离**是进程模型的核心价值：进程 A 崩溃不会波及 B——每个进程以为自己独占内存（虚拟地址），MMU 把地址翻译到物理页。这也是"进程间为什么需要 IPC"的原因：隔离的代价是通信要走显式通道。

## 2. 线程：调度的最小单位

线程共享进程的地址空间与资源，但各自有：**栈、寄存器状态、程序计数器**。对比：

| 维度 | 进程 | 线程 |
| --- | --- | --- |
| 地址空间 | 独立（隔离） | 共享（通信零拷贝） |
| 创建/切换成本 | 高（页表+地址空间） | 低（只换栈与寄存器） |
| 崩溃影响 | 只死自己 | 连累整个进程 |
| 通信 | IPC（管道/共享内存/socket） | 共享变量（需加锁） |
| 适用 | 多用户/多任务隔离 | 同一任务内并行 |

**进程 vs 线程的选择逻辑**：需要故障隔离或权限边界选进程（浏览器每个 Tab 一个渲染进程、Nginx worker）；需要高频共享数据选线程（图像处理、游戏引擎）。

## 3. 调度算法：五种经典策略

| 算法 | 规则 | 优点 | 缺点 |
| --- | --- | --- | --- |
| FCFS 先来先服务 | 按到达顺序 | 公平、实现简单 | 短作业被长作业阻塞（护航效应） |
| SJF 短作业优先 | 运行时间最短先跑 | 平均等待时间理论最优 | 长作业可能饿死；运行时长需预测 |
| Round Robin 时间片轮转 | 每进程跑一个时间片 | 响应快、公平 | 时间片太短→切换开销；太长→退化 FCFS |
| Priority 优先级 | 高优先级先跑 | 重要任务及时 | 低优先级饿死（需老化机制） |
| MLFQ 多级反馈队列 | 新任务进高优先级队列，用完时间片降级 | 兼顾响应与吞吐，无需预知时长 | 实现复杂 |

**MLFQ 的精髓**（OSTEP 教材的招牌设计）：不知道任务长短没关系——先给它最高优先级（长任务会因用完时间片被逐级降级，短任务在上层就完成）。**老化（aging）**：等待越久优先级越高，防饿死。

## 4. 上下文切换：性能的隐形杀手

切换线程时，内核要保存/恢复：寄存器、程序计数器、栈指针、部分缓存失效（TLB flush、CPU 缓存污染）：

```
保存当前线程上下文 → 切换 rsp 到新线程栈 → 恢复新线程上下文 → 跳到 PC
```

实测量级：同进程线程切换 ~1-10 微秒；进程切换更贵（页表切换 + TLB 失效）。**现代架构的优化**：

- **用户态线程（协程）**：Go goroutine、Erlang 轻量级进程——切换不进内核，纳秒级
- **进程/线程亲和性**（taskset、cpuset）：绑核避免迁移导致的缓存冷启动
- **避免过度切分**：高频切换的收益若小于开销（每秒百万级上下文切换是病态信号）

`vmstat` 的 `cs` 列、`pidstat -w` 的 cswch/s 可直接观测切换频率。

## 5. 进程间通信（IPC）五件套

| 机制 | 特点 | 场景 |
| --- | --- | --- |
| 管道（pipe） | 单向字节流，父子进程 | shell 管道 `\|` |
| 消息队列 | 结构化消息、内核维护 | 松耦合任务分发 |
| 共享内存 | **最快**（零拷贝），需自己同步 | 大数据量高频通信 |
| 信号量/互斥锁 | 控制并发访问 | 配合共享内存 |
| Unix domain socket | 双向、支持文件描述符传递 | 本地 RPC（Docker daemon） |

**共享内存 + 信号量**是性能之王（没有内核拷贝），但同步全靠自己——忘加锁就是玄学 bug。跨机器的 IPC 就是网络（socket），回到站内《TCP 深入》。

## 6. 线程安全：从锁到无锁

```c
// 竞态条件：读-改-写不是原子的
counter++;          // 实际是 load → add → store 三步

// ① 互斥锁（正确但可能阻塞）
pthread_mutex_lock(&m); counter++; pthread_mutex_unlock(&m);

// ② 原子指令（硬件级，无锁）
atomic_fetch_add(&counter, 1);     // x86 LOCK XADD 前缀

// ③ CAS 无锁（乐观并发）
old = atomic_load(&counter);
do { new = old + 1; }
while (!atomic_compare_exchange(&counter, &old, new));   // 失败则重读重试
```

**CAS 的两难**：无等待但可能活锁（重试风暴）。Java 的 `synchronized` 从偏向锁→轻量级锁→重量级锁自适应升级，本质是"先乐观后悲观"的工程折中。

## 7. 死锁：四个必要条件与破解

死锁要求**同时**满足四条件：互斥、持有并等待、不可剥夺、循环等待。

| 破解策略 | 做法 | 代价 |
| --- | --- | --- |
| 破坏循环等待 | 全局锁序（所有线程按同一顺序拿锁） | 需要设计期约定 |
| 破坏持有并等待 | 一次性拿全所有锁（tryLock 全套） | 可能总拿不全 |
| 破坏不可剥夺 | 拿不到就释放已持有的 | 适合可重试操作 |
| 检测恢复 | 资源分配图检测环，回滚 | 运行时开销 |

**实践首选锁序**：`lock A → lock B` 与 `lock B → lock A` 是死锁对——规定所有代码 `A → B` 获取即根除。数据库的死锁检测（InnoDB 回滚代价小的事务）属于检测恢复派。

## 8. 陷阱速查表

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 高 CPU 但单核没跑满 | 上下文切换过频（线程风暴） | 减线程数/绑核；用线程池 |
| 共享内存数据随机损坏 | 忘同步或锁粒度错 | 原子操作/互斥锁/串行化 |
| 程序偶发卡死 | 死锁（四条件满足） | 统一锁序或 tryLock 超时 |
| 线程内变量串号 | 线程复用没清 ThreadLocal | finally 中 remove() |
| 多进程抢同一文件写坏 | 缺互斥 | flock/文件锁或单写者模式 |
