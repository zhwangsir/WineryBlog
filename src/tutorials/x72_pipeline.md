## 1. 流水线：把洗衣店变成工厂

非流水线的洗衣流程（洗 40 分钟 → 烘 40 → 叠 20 = 100 分钟/批）改成流水线——洗完一批立刻烘，同时下一批开洗——**每批实际间隔 = 最长工序**。CPU 同理，经典五级：

| 级 | 名称 | 做什么 |
| --- | --- | --- |
| IF | 取指 | 从内存取指令 |
| ID | 译码 | 解析指令、读寄存器 |
| EX | 执行 | ALU 运算 |
| MEM | 访存 | 读/写内存（Load/Store） |
| WB | 写回 | 结果写回寄存器 |

理想加速比 = 级数（5 级 ≈ 5 倍）。**实际达不到**的原因就是三类冒险——流水线"停顿"（stall/气泡）的三大来源。

**流水线寄存器**：每级之间有一组寄存器（IF/ID、ID/EX...）保存上一级的输出——它们是流水线的"传送带"，时钟沿推动所有指令同时前进一级。

## 2. 结构冒险：硬件冲突

两条指令同时需要同一硬件。经典案例：ID 要读寄存器、MEM 要访存——若寄存器堆只有一个写口，IF 取指与 MEM 取数据同时访问内存（单口存储器时代）。

**修法**：加硬件资源（分离的指令/数据缓存——哈佛结构的 I-Cache/D-Cache 就是这么来的；寄存器堆做成同周期前半写/后半读）。现代 CPU 中结构冒险已被硬件资源基本消除，出现概率最低。

## 3. 数据冒险：下一条要用上一条还没算完的结果

```assembly
add x1, x2, x3      # x1 在 EX 结束才有值
sub x4, x1, x5      # 需要读 x1 —— 但 x1 还没写回！
```

**方案一： stall（气泡）**——sub 在 ID 等两个周期直到 add 的 WB 完成。正确但浪费 2 拍。

**方案二：转发/旁路（forwarding/bypassing）**——add 在 EX 结束时结果其实已经在 ALU 输出端了，直接用一根旁路总线把它**从 EX/MEM 流水线寄存器引到 EX 的输入**——不用等 WB：

```
EX/MEM.res ──转发──→ EX 输入 A/B   （ALU→ALU，零停顿）
MEM/WB.res ──转发──→ EX 输入        （Load→紧邻指令）
```

**Load-Use 冒险**（无法完全转发的特例）：Load 的数据在 MEM **结束**才可用，紧随其后的指令 EX 需要——转发赶不上，**必须 stall 一拍**：

```assembly
lw  x1, 0(x2)       # x1 在 MEM 结束才有
add x3, x1, x4      # 必须停 1 拍（编译器可重排指令填补气泡）
```

编译器/硬件的指令调度就是往这个气泡里塞一条无关指令。

## 4. 控制冒险：分支打乱取指流

条件分支要等 EX 甚至更晚才知道"跳不跳、跳到哪"——这期间 IF 已经取了后续指令（一旦跳转，取的全是废指令）。**分支在典型程序中每 5-6 条出现一条**，控制冒险是性能的头号敌人。

| 方案 | 原理 | 准确率 |
| --- | --- | --- |
| stall | 分支解析前不取指 | 正确但每分支浪费 1-2 拍 |
| 静态预测 | 恒猜不跳 / 向后跳猜跳（循环）、向前猜不跳 | 60-90% |
| 动态预测（1 位饱和计数器） | 记录上次方向 | 循环边界必错两次 |
| **2 位饱和计数器** | 连错两次才改变预测方向 | 循环只错一次，>90% |
| **BTB 分支目标缓冲** | 缓存"分支 PC → 目标 PC"，IF 阶段就查 | IF 即可跳到目标，零气泡 |

现代 CPU 的动态预测器进化到 TAGE/感知机（准确率 >95%），用历史模式表捕捉复杂分支行为——预测错误的代价是**清空整条流水线**（深度流水线 15-20 级的 mispredict penalty 极痛），这就是为什么分支友好的代码（减少不可预测分支）能实测提速。

**推测执行（speculation）**：预测器说跳就先跳着执行——猜对了白赚，猜错了全流水线冲刷回滚。幽灵漏洞（Spectre）正是推测执行留下的安全侧信道——性能与安全的权衡缩影。

## 5. 超标量与乱序：流水线的进化

- **超标量**：一个周期发射多条指令（多条并行流水线），理论加速比 = 级数 × 发射宽度
- **乱序执行**：指令按依赖关系就绪即执行，不按程序顺序——硬件寄存器重命名消除"假依赖"（WAR/WAW），ROB（重排序缓冲）保证按序提交结果
- **超线程（SMT）**：一颗物理核伪装两个逻辑核，用一个核的执行资源同时喂两个线程的指令流——利用彼此的空闲单元

## 6. 陷阱速查表

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 紧跟 Load 的运算变慢 | Load-Use 冒险停 1 拍 | 编译器重排/提前发 Load |
| 分支密集代码慢 | 预测失败冲刷流水线 | 减少不可预测分支（分支消除） |
| 循环展开能提速 | 减少分支判断次数 | 适度展开（过量胀大 I-cache 反慢） |
| 排序后再处理更快 | 分支预测对有序数据友好 | 保持可预测的分支模式 |
| 同逻辑汇编更快 | 指令调度填了冒险气泡 | 信任编译器 -O2 |
