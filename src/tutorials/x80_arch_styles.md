## 1. 架构的定义：重要且难以改变的决策

> **架构 = 重要决策的集合，重要 = 改起来代价高。**（Ralph Johnson）

架构不是画一堆框图，而是回答四类问题：
1. **结构**：系统由哪些模块/服务组成？边界在哪？
2. **依赖方向**：谁依赖谁？（依赖规则是架构的灵魂）
3. **数据流**：请求怎么流动、状态存哪、如何同步？
4. **技术选型**：语言/框架/存储/通信协议

**架构风格（Architectural Style）**= 一族约束的命名（如分层、事件驱动、微服务）——类比建筑里的哥特式/现代主义。风格不是套模板，是**一组可协商的约束**，理解约束的意图才能正确裁剪。

## 2. 分层架构：最经典的依赖规则

```
┌─ 表现层（UI/API）────────────┐
├─ 业务层（领域逻辑）──────────┤   依赖只能向下！
└─ 数据层（持久化/外部）────────┘
```

- **优点**：关注点分离、人人会懂、团队按层分工
- **缺点**：业务层容易变"透传层"（贫血模型）；跨层改动要贯穿；性能多一层开销

**分层的铁律是依赖方向**：上层依赖下层，下层绝不知晓上层。违反的典型：业务层 import 了 HTTP request 对象——把 Web 框架的细节漏进了领域逻辑，换框架就要重写业务。

**变体**：干净架构/洋葱架构把依赖规则推到极致——**依赖永远指向领域层**（领域不依赖任何东西，框架/DB 是被领域定义的插件）。代价是大量映射样板，收益是领域逻辑的完全框架无关。

## 3. 六边形架构（端口与适配器）：领域为中心

```
            ┌── HTTP 适配器 ──┐
REST/RPC ──→│                │──→ 业务核心（领域逻辑 + 端口接口）
            └── gRPC 适配器 ──┘         │
            ┌── DB 适配器 ─────┘        │（核心只依赖端口接口）
DB ────────→│                │←── 实现
```

核心概念：
- **端口（Port）**：核心定义的接口（"我需要一个存储用户的东西"）
- **适配器（Adapter）**：外部技术的实现（MySQL 实现、Redis 实现、HTTP 入口）
- **依赖反转**：核心不 import 适配器，适配器实现核心的接口

**收益**：换数据库/换框架只写新适配器；业务逻辑可脱离框架做纯单元测试。**代价**：接口与映射的样板代码。**适用判据**：核心领域逻辑复杂且长期演进（支付、计价、风控）值得保护；简单 CRUD 用分层更直接。

## 4. 事件驱动架构：用消息解耦时空

```
服务A ──发布事件──→ [消息代理] ──订阅──→ 服务B（异步处理）
                              └──订阅──→ 服务C
```

- **解耦**：A 不知道 B/C 的存在——新增消费者零改动（对比同步调用：A 要改代码调用 C）
- **异步**：A 发完即走——削峰（见站内《消息队列入门》）
- **最终一致**：B/C 的处理有延迟——**业务必须接受窗口期不一致**

**两种事件风格**：
- **事件通知**（"订单已创建"，含发生了什么）——消费者自行查询详情，松耦合
- **事件携带状态转移**（事件里带上完整数据）——消费者免查库，耦合事件结构

**陷阱**：事件顺序无保证、重复投递（消费方要幂等）、难调试（跨服务追踪）——**可观测性（链路追踪）必须先建**。

## 5. 单体 vs 微服务：拆分时机决策

| 维度 | 模块化单体 | 微服务 |
| --- | --- | --- |
| 部署 | 一个包 | 独立部署 |
| 事务 | 本地事务 | 跨服务 Saga/最终一致 |
| 团队 | 一个团队内协作 | 按服务划分自治团队 |
| 基建 | 简单 | 服务发现/网关/追踪全套 |
| 调试 | 一个进程断点 | 分布式追踪 |

**反共识警告**：微服务是**组织问题的解法**（Conway 定律：系统结构镜像组织沟通结构）——不是性能解法也不是技术先进性象征。**过早微服务 = 分布式单体**（拆了服务还要一起部署，却背上全部分布式复杂度）。

**演进路线**：模块化单体（模块边界清晰、接口隔离）→ 团队与边界长大后，沿**已验证的模块边界**拆出微服务。**单体里画不出清晰的模块边界，微服务里更画不出**。

## 6. CQRS：读写分离的架构模式

```
写模型（命令）→ 校验+变更 → 写库 ──事件──→ 投影 ──→ 读模型（反规范化视图）
读查询 ←──────────────────────────── 读模型
```

写模型保证业务规则，读模型按查询形状反规范化——**读写各自最优**。代价：最终一致（读模型滞后）、投影维护成本。适用：读写负载悬殊（读多写百倍）、读形状复杂多变。小系统别上 CQRS——两个模型维护翻倍。

## 7. 架构决策记录（ADR）：让决策有据可查

```markdown
# ADR-007: 采用事件驱动解耦订单与库存
状态：已接受
背景：订单高峰期库存服务同步调用拖慢下单 P99
决策：订单完成后发布 OrderCreated 事件，库存异步扣减
后果：+ 下单延迟降低；- 库存扣减最终一致（接受 1s 窗口）；+ 可加新消费者
```

一文件一决策（含背景/选项/决策/后果），进 git 随代码演进。**三个月后没人记得为什么这么设计**——ADR 就是团队的记忆。

## 8. 陷阱速查表

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 业务层全是透传 | 贫血模型（数据与行为分离） | 充血建模：行为进领域对象 |
| 换框架要重写业务 | 领域依赖框架 | 六边形：依赖反转到端口 |
| 微服务间同步调用链过长 | 服务拆分边界错误/同步编排 | 事件驱动异步编排；合并服务 |
| 事件消费者重复处理 | 消息至少一次投递 | 消费方幂等（去重键） |
| 架构图与代码对不上 | 图是"愿望"没更新 | ADR + 模块结构即文档（依赖检查进 CI） |
| 分布式单体 | 拆服务但一起部署 | 按独立部署与数据所有权重划边界 |
