## 1. 重构的精确定义

> **重构（Refactoring）= 在不改变软件可观察行为的前提下，调整其内部结构以提高可理解性并降低修改成本。**（Martin Fowler）

三个关键词划清边界：
- **不改变行为**：加功能不是重构，是"加功能时顺便重构"（两顶帽子——每次只戴一顶）
- **不改性能**：性能优化是另一回事（可能改行为约束）；重构以结构为先，性能靠 profile 另行优化
- **以修改成本为纲**：重构的收益不体现在当下，体现在**下一次改动**更快更安全

**为什么重构**：代码是"负债"——每次需求变化都要在旧结构上绕行，绕行成本随时间复利。重构是**还债**：当下花 1 小时，未来每次改动省 10 分钟。

## 2. 代码坏味道精选（闻起来该重构了）

Fowler 的坏味道清单实战精选：

| 坏味道 | 信号 | 常见重构方向 |
| --- | --- | --- |
| 神秘命名（Mysterious Name） | 名字需要注释才能懂 | 改名（Rename） |
| 重复代码 | 同样的逻辑出现两处以上 | 提取函数/提取类 |
| 过长函数 | 一屏放不下、多层嵌套 | 提取函数（按意图分层） |
| 发散式变化 | 一个类因多种原因被反复修改 | 拆类（按变化方向分离） |
| 霰弹式修改 | 一个需求要改 N 个文件 | 搬移函数/字段聚合 |
| 依恋情结 | 函数大量使用别的类的数据 | 搬移函数到数据所在类 |
| 数据泥团 | 几个字段总是一起出现 | 提取类/引入参数对象 |
| 基本类型偏执 | 用字符串表示电话/金额/日期 | 值对象（域模型化） |
| 重复 switch | 多处同构 switch | 多态/查表替换 |
| 注释滥用 | 注释在解释"烂代码在干什么" | 先重构让代码自解释，注释留意图 |
| 夸夸其谈通用性 | 为想象中的未来建抽象 | 删掉，规则三法则后再抽象 |

**判定心法**：坏味道不是"违反规则"，是"未来修改会痛的预警信号"。同样一段长函数，算法步骤清晰自解释可以不动；逻辑纠缠变量复用混乱就必修。

## 3. 安全手法精选（每个都小步可验证）

### 提取函数（Extract Function）
```javascript
// 重构前：长函数里一段逻辑需要注释才看得懂
function printOwing(invoice) {
  let outstanding = calcOutstanding(invoice);
  // 打印账单头
  console.log('**** 账单 ****');
  console.log(`客户: ${invoice.customer}`);
  console.log(`金额: ${outstanding}`);
}

// 重构后：注释消失——函数名就是注释
function printOwing(invoice) {
  printBanner();
  const outstanding = calcOutstanding(invoice);
  printDetails(invoice, outstanding);
}
```

**为什么最常用**：长函数是万恶之源；提取是所有其他重构的准备工作。要点：局部变量少（易提取）、提取后**跑测试**再继续。

### 引入参数对象（Introduce Parameter Object）
```javascript
// 重构前：数据泥团成群出现
function charge(lastReading, currentReading) { ... }

// 重构后：聚合成领域概念
function charge(reading) { ... }     // Reading { customer, date, amount }
```

参数对象往往暴露"缺一个领域类"——重构顺带改进领域模型。

### 以多态取代条件表达式（Replace Conditional with Polymorphism）

```javascript

```

判据：函数引用了哪个类的数据最多就搬到哪。这是"数据与行为聚合"（封装）的核心手法。

## 4. 安全网：测试是重构的前提

**铁律：没有测试的重构 = 拿生产环境赌命。**重构前后行为必须一致——**靠测试证明**，不靠"我确认没问题"。

- 先补测试再重构（给要动的区域铺快照/单测）
- **小步走**：一个手法 → 跑测试 → 提交（git 提供无限次后悔药）
- IDE 自动重构（重命名/提取/内联）**优先于手改**——它保证所有引用点同步更新

```bash
# 小步循环
改一小步 → npm test → git commit -m "refactor: 提取 printDetails" → 下一步
```

## 5. 遗留代码的重构时机

"没时间重构"是常态——用**童子军军规**（每次路过让代码更干净一点）+ **机会主义重构**：

```text
准备改 ModuleA 加功能 → 发现 ModuleA 乱 →
先花 30 分钟把"本次要动的部分"重构到能优雅加功能 → 测试 → 提交 → 再加功能
```

**不重构整个系统**——只重构"本次改动要触碰的区域"（预备性重构）。大重构立项的标准：改动的预估成本已显著超过重构成本，且有独立验证窗口。

## 6. 技术债的账本思维

技术债 = 快速交付借的结构债，利息 = 每次后续改动的额外成本。管理要点：
1. **显式登记**：TODO/FIXME 带上下文与预估工时（不要无息借贷）
2. **定期盘点**：改动热点文件（git 热区）× 复杂度 = 重构优先级
3. **区分四种债**：故意为之（有记录）/ 无意疏忽 / 业务必需妥协 / 历史遗留——应对策略不同
4. **利息可视化**：新需求在烂区的实际工时 ÷ 理想工时 = 利率——用数据说服管理层排重构

## 7. 陷阱速查表

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 重构后行为变了 | 没测试兜底/改了可观察行为 | 先补测试；两顶帽子分开戴 |
| 大爆炸式重构搞崩上线 | 一次性大改+长分支合并地狱 | 小步多次；绞杀者模式渐进替换 |
| 越重构越复杂 | 为抽象而抽象/过度设计 | 回到具体问题；规则三法则 |
| 重构完性能下降 | 结构优化与性能优化混淆 | 先重构再 profile 优化性能 |
| 团队说"没空重构" | 无数据支撑 | 用改动热点×利率数据立项 |
