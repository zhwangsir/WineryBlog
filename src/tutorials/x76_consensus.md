## 1. 共识问题：分布式系统的皇冠

**共识（Consensus）**：一组节点在"部分节点会挂、消息会丢会乱序"的环境下，对一个值达成一致。

它是无数上层问题的归一：谁是主节点（leader election）、锁归谁（distributed lock）、配置是什么、日志的顺序是什么——**一切都能归约为"就一系列日志达成一致"（ replicated log）**。Paxos 与 Raft 就是为解决它而生。

难点在于：网络分区、消息乱序/丢失、节点慢——**协议必须在任何这些扰动下仍然安全**（不同节点不会做出矛盾的决议）。

## 2. 核心武器：多数派（Quorum）

一切共识协议的地基是**多数派交集原理**：

> 两个"多数派"（N/2+1 个节点）必然至少共享一个节点。

如果每次决议要求**多数派节点确认**，那么两个先后决议的确认集合必有交集——交集节点见证了第一次决议，能阻止第二次矛盾决议。这就是 Paxos 的灵魂：**决议一旦被多数派接受就不可逆转**（除非有更新的多数派明确覆盖）。

N=5 时容忍 2 节点失败（3/5 仍构成多数派）。**为什么奇数**：偶数节点不增加容错能力（4 与 3 同样容忍 1 个失败）却增加成本与延迟。

## 3. Basic Paxos：两阶段决议

角色：Proposer（提议者）、Acceptor（接受者）、Learner（学习者）。

```
阶段一 Prepare：
  Proposer: 提出编号 n（全局递增），向多数派 Acceptor 发 Prepare(n)
  Acceptor: 若 n > 已承诺的最大编号 → 承诺不再接受编号 ≤ n 的 Prepare，
            并返回自己"已接受"的最大编号决议（若有）

阶段二 Accept：
  Proposer: 若多数派响应 → 提议 Accept(n, v)
            v = 响应中编号最大的已接受值；若无已接受值 → 用自己的提案值
  Acceptor: 若 n ≥ 已承诺编号 → 接受 (n, v)
多数派接受 → 决议达成（v 被选定）
```

**两个精妙设计**：
1. **Prepare 的承诺机制**让后来者"尊重"已有的决议——只要多数派接受过 v，任何新 Proposer 的 Prepare 都会从响应中学到 v 并沿用（决议不可覆盖）
2. **编号决定发言权**——编号小的提案会被拒绝，避免两个 Proposer 互相覆盖死锁

**活锁问题**：两个 Proposer 交替提高编号、互相打断——Basic Paxos 理论上可能无限循环（Lamport 论文标题 The Part-Time Parliament 之谜）。解法：选出**唯一的 Proposer**（Leader）——这就是 Multi-Paxos 与 Raft 的出发点。

## 4. Multi-Paxos：连续决议的工程化

Basic Paxos 每决议一个值都要跑两阶段（2 次多数派往返）——日志系统要连续写几千条，太慢。**Multi-Paxos 的优化**：选出稳定的 Leader 后，阶段一（Prepare）只需执行一次，之后 Leader 直接跳过 Prepare 连续发起 Accept——每条日志只剩一次多数派往返。

## 5. Raft：为可理解性重新设计

Paxos 以难懂著称（Lamport 自己的论文都被拒稿两次）。Raft（2014）目标明确：**与 Paxos 等价，但分解成三个可独立理解的子系统**——领导选举、日志复制、安全性。

### 子系统一：领导选举

- 全体节点三种角色：Leader / Follower / Candidate
- Leader 心跳维持权威；Follower 超时未收到心跳 → 变 Candidate → 发起拉票（RequestVote）→ **多数派投票** → 当选
- **随机化选举超时**（如 150-300ms 随机）——避免多 Candidate 同时拉票导致选票分裂；输了的退回 Follower 等下一轮

投票规则保证安全性：
1. 每个节点**一个任期只投一票**（先到先得）
2. 只投给"日志不落后于自己"的候选人（比较最后日志条目的任期号与下标）——**保证当选者拥有全部已提交日志**

### 子系统二：日志复制

```
客户端写 → Leader 追加日志 → 并行发给所有 Follower
Follower 追加成功回执 → Leader 收到多数派回执 → 提交该条目（应用到状态机）
→ 通知 Follower 提交 → 回复客户端
```

日志是**顺序一致**的：下标与顺序全局确定，Follower 与 Leader 日志逐条对齐（不一致时 Leader 强制覆盖 Follower 的分歧后缀）。

### 子系统三：安全性（提交规则）

**关键规则：Leader 只能直接提交"当前任期"的日志条目；旧任期的条目随新条目间接提交。**（Raft 论文 Figure 8 的反例场景：不满足此规则，已复制到多数派的旧任期日志可能被覆盖。）加上"选举限制"（§5 的投票规则 2），共同保证**已提交的日志永不被覆盖**——这是共识的安全底线。

### 其他机制
- **成员变更**（加节点/删节点不停服）：联合共识（两阶段切换配置）或单步变更
- **日志压缩/快照**：日志太长 → 把已应用状态打成快照，丢弃旧日志（配合 InstallSnapshot 给落后节点）
- **读优化**：ReadIndex/lease read——读不走日志（线性一致读的轻量实现）

## 6. Paxos vs Raft 对照

| | Paxos | Raft |
| --- | --- | --- |
| 出发点 | 正确性证明优先 | 可理解性优先 |
| 角色 | 对等的 Proposer/Acceptor | 强 Leader（一切写经 Leader） |
| 决议单位 | 单值（Basic）| 日志条目（Multi） |
| Leader | 隐式（Multi-Paxos 才显式化） | 显式选举 + 任期机制 |
| 生态 | 论文实现少 | etcd/Consul/TiKV/JRaft 大量生产实现 |

**生产建议**：不要自己实现——用 etcd/Consul（现成共识服务）或成熟库（etcd-raft 模块）。

## 7. 陷阱速查表

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 频繁重新选举 | 选举超时 < 心跳间隔/网络抖动 | 超时 >> 心跳间隔；随机化范围加大 |
| 节点日志对不上 | Leader 覆盖分歧后缀正常现象 | 确认提交规则未被绕过 |
| 读到旧值 | 直接读本地状态机（未过日志） | ReadIndex / lease read（线性一致读） |
| 3 节点挂 2 全瘫 | 多数派无法达成 | 按容错需求配 N（3 容 1，5 容 2） |
| 部署跨机房延迟高 | 多数派确认跨机房 RTT | 机房内多数派 + 跨机房异步；或地域分片 |
