## 1. 为什么要分布式：单机的三堵墙

任何单机系统终将撞上：

1. **容量墙**：数据超过单机磁盘/内存上限（TB-PB 级）
2. **性能墙**：单核/单机的吞吐与延迟天花板（纵向扩容的边际成本陡增）
3. **可用性墙**：单机/单机房 = 单故障域（机器挂了服务全挂）

分布式的解法是**把一台变成多台**：数据分片（解决容量）、副本冗余（解决可用性）、并行处理（解决性能）。代价——**网络是不可靠的、延迟是显著的、机器是会挂的**，一致性从"理所当然"变成"需要精心设计"。

## 2. CAP 定理：三选二的精确含义

**CAP**：一致性（Consistency）、可用性（Availability）、分区容忍（Partition tolerance）不可同时全得。

- **一致性（C）**：线性一致——所有节点在同一时刻看到相同的数据
- **可用性（A）**：每个请求都能得到（非错误的）响应
- **分区容忍（P）**：网络分区（节点间断连）发生时系统仍能工作

**证明直觉**：网络分区把集群切成两半，客户端在 A 区写入新值——B 区若要保持一致必须拒绝读写（牺牲 A 可用性）；若要可用必须接受旧值（牺牲一致性）。**分区发生时 C 与 A 只能二选一**。

三个常见误解澄清：
1. **不是"永远三选二"**——没有分区时（网络正常）C 与 A 可以兼得；CAP 说的是**分区发生的那一刻**必须取舍
2. **P 不是可选项**——分布式系统必然存在分区可能，放弃 P 就是放弃分布式（回到单机）
3. 实际是 **PACELC**：分区（Partition）时选 C 或 A；**否则（Else）** 选延迟（Latency）或一致——同步复制=低延迟让位一致性，异步复制=高延迟换可用性

**实践映射**：CP 系统（ZooKeeper/etcd/HBase）——分区时少数派拒绝服务，保一致；AP 系统（Cassandra/DynamoDB/Eureka）——分区时继续服务，接受暂时不一致（最终一致）。

## 3. 一致性模型谱系：从强到弱

一致性不是二元的，是一个光谱：

| 模型 | 保证 | 成本 | 典型 |
| --- | --- | --- | --- |
| **线性一致** | 所有操作像在单机上按某种全局顺序瞬间完成 | 最贵（多数派确认） | etcd、ZooKeeper |
| 顺序一致 | 同一进程的操作顺序保持，全局顺序可能不同 | 中 | ZooKeeper 默认读 |
| 因果一致 | 有因果关系的操作全节点看到相同顺序 | 较低 | 评论/会话场景 |
| **最终一致** | 停止写入后，"最终"所有副本收敛 | 最低 | Cassandra、DNS |

**读己之写**（read-your-writes）：用户写完立刻读——至少要读到自己刚写的（会话粘性/读写主库解决）。**单调读**：同一用户多次读不出现"时光倒流"（粘住同一副本）。

**选型原则**：金融余额/库存扣减 → 线性一致；社交点赞/浏览数 → 最终一致足矣。**用错强一致的代价是延迟与可用性，用错最终一致的代价是业务逻辑漏洞**——先问业务能否接受窗口期不一致。

## 4. 复制策略：副本怎么同步

### 主从复制（Leader-based，主流）
```
客户端 → Leader（负责所有写）→ 同步给 Follower
读：可从 Leader 或 Follower 读（异步复制时 Follower 有滞后）
```
- **同步复制**：等全部 Follower 确认——一致性强，延迟高、可用性差（一台挂就卡）
- **异步复制**：发完就回——快，但 Leader 挂可能丢最后几条
- **半同步**：至少 1 个 Follower 确认——折中（MySQL 半同步复制）

### 多主与无主
- **多主复制**（Multi-Leader）：多个主各自接受写，互相同步——跨数据中心低延迟写，但**冲突解决**复杂（LWW 时间戳丢弃/CRDT 合并）
- **无主复制**（Dynamo 风格）：写入 W 个副本、读取 R 个副本，N 为副本总数——**W + R > N 时读写集合必有交集**，能读到最新写入（quorum 读旧值检测）。典型 N=3, W=2, R=2

## 5. 故障模型与故障检测

| 故障类型 | 表现 | 应对难度 |
| --- | --- | --- |
| 崩溃故障（crash） | 挂了就是不响应 | 易（超时判定） |
| 遗漏故障 | 丢消息 | 中 |
| 时序故障 | 响应慢/时钟漂移 | 难（"慢"与"挂"难区分） |
| 拜占庭故障 | 任意行为（篡改/撒谎） | 最难（需 BFT 算法，3f+1 节点） |

**故障检测的本质难题**：网络里"慢"与"死"不可区分——只能用**超时+心跳**的概率性判定（φ 值accrual检测器输出"怀疑程度"而非布尔）。误判会把健康主节点错杀——需要法定人数（quorum）机制防误杀（如哨兵的多数派投票）。

## 6. 分布式事务：跨节点的一致性难题

| 方案 | 机制 | 代价 |
| --- | --- | --- |
| **2PC 两阶段提交** | 协调者先问全部"能否提交"（投票）再统一下令 | 阻塞（协调者挂则锁悬置）；同步开销 |
| 3PC | 加 pre-commit 阶段缓解阻塞 | 复杂，仍非完全安全 |
| TCC | Try（预留）→ Confirm/Cancel 业务层补偿 | 侵入业务，每个操作写三个接口 |
| Saga | 长事务拆分 + 每步配补偿动作 | 最终一致，不隔离中间状态 |
| 本地消息表 | 事务与消息同库落盘，异步投递 | 简单可靠（国内电商常用） |

2PC 的"协调者单点"由共识算法补足（Raft 化的协调者），这是 NewSQL（TiDB 的 Percolator 变体）的路线。**能不用分布式事务就不用**——拆分业务让事务落在单库内，跨库用最终一致（消息表/Saga）。

## 7. 陷阱速查表

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 写后读不到（别人机器上） | 异步复制滞后 | 读己之写（粘主库/会话） |
| 双主写入数据互相覆盖 | 多主无冲突解决 | 明确冲突策略或单主 |
| 2PC 卡死在投票阶段 | 协调者崩溃 | 协调者高可用（共识化） |
| quorum 读写仍读到旧值 | W+R>N 但读集合与写集合错开节点 | 动态调整副本/读写修复 |
| 心跳超时频繁误判主挂 | 网络抖动/GC 停顿 | 心跳容忍窗口调大；长 GC 治理 |
| 跨机房延迟高 | 同步复制跨机房 RTT | 机房内同步+机房间异步 |
