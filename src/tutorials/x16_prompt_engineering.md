## 1. Prompt 为什么是"工程"

大模型像一位**读过全网资料但没有任何你上下文的顾问**。Prompt 工程就是把三件事讲清楚：

1. **你是谁**（角色）
2. **你要什么**（任务 + 边界）
3. **怎么交付**（格式 + 标准）

同一问题，Prompt 质量不同，结果天差地别：

```
✗ 帮我写个周报
✓ 你是互联网团队的项目经理。根据我下面的流水记录，写一份
  给部门总监的周报：分「本周进展/风险/下周计划」三节，每节
  不超过 3 条，语气客观精炼，不写废话。
  流水：…
```

## 2. 五个核心技巧

### ① 角色锚定
给模型一个专业身份，激活对应领域的表达模式：

```
你是一位有 10 年经验的后端架构师，擅长把复杂问题讲给初级工程师听。
```

### ② 结构化上下文
用分隔符明确区分「材料」和「指令」，防止模型混淆：

```
请基于 <资料> 回答问题，资料之外的不要编造。

<资料>
{text}
</资料>

问题：{q}
```

### ③ 少样本示例（Few-shot）
给 2-3 个输入输出示例，模型会模仿格式与风格：

```
把报错翻译成人话：
输入: TypeError: cannot read 'map' of undefined
输出: 你在 undefined 上调用了 .map()，通常是数组没初始化或异步数据还没回来。

输入: EADDRINUSE: address already in use :3000
输出: 3000 端口被占用——上一个进程没杀干净，换个端口或 kill 掉旧进程。
```

### ④ 思维链（Chain of Thought）
要求「一步一步推理」能显著提升数学/逻辑类任务质量：

```
请一步步推理：先列出已知条件，再逐条推导，最后给出结论。
```

### ⑤ 结构化输出
指定格式，下游代码才能稳定解析：

```
以 JSON 输出，schema：{"sentiment": "pos|neg|neutral", "score": 0-1, "reason": ""}
只输出 JSON，不要多余文字。
```

## 3. 高级模式

### 分解（把大任务拆小）
写 5000 字报告会崩，但「先列大纲 → 逐节扩写 → 统一润色」三步很稳。**与模型协作 = 好的甲方：目标清晰、步骤拆细、每步验收。**

### 自我批改
```
先草拟答案，然后以挑剔审稿人身份列出 3 个问题，再据此改出终稿。
```

### 兜底指令
```
如果资料里没有答案，回答「资料中未提及」，禁止编造。
```
（RAG 场景必备，抑制幻觉。）

## 4. 常见坑

| 坑 | 现象 | 对策 |
| --- | --- | --- |
| 指令太客气 | 「麻烦帮我写个大概之类的」 | 明确动词：生成/翻译/改写/评分 |
| 多任务混杂 | 一段话让它又翻译又总结 | 拆成多轮，或编号分步 |
| 关键约束埋没 | 要求写在长文中间 | 约束放开头或结尾，加粗强调 |
| 无边界 | 模型自由发挥编造 | 给「不知道就说不知道」的许可 |

## 5. 迭代：Prompt 是调出来的

把 Prompt 当代码：**版本化 + 对照测试**。准备 5 个典型输入，改一版跑一遍，记录效果，直到稳定。官方文档和模型都会升级，Prompt 也要维护。
